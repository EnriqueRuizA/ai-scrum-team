Respuestas del usuario (2026-09-30):
  D1. Motor principal = MODELOS GRATUITOS DE OPENCODE. El proyecto usa opencode
      como motor agentico; dentro de opencode se configura el proveedor gratis
      (Ollama local: ollama/llama3.2 para chat, mas embeddings si se necesitan)
      y/o proveedores free (NVIDIA build, Cerebras, OpenRouter free, etc.).
  D2. El repo NO tiene remoto publico -> se DESCARTA reescribir historial y
      force-push. Basta con des-trackear secretos y commitear la limpieza.
  D3. Integraciones Claude/OpenAI se MANTIENEN como OPCIONALES, pero como
      simples proveedores configurables dentro de opencode, sin codigo acoplado
      en el proyecto.
  D4. generar_mapa.py SE BORRA (el grafo de Obsidian lo cubre).
  D5. project_schema.json SE BORRA (el grafo de Obsidian lo cubre). Tambien se
      borran GRAPH_MAP.md y architecture.html por el mismo motivo.

Decisiones tecnicas por defecto (recomendadas, configurables):
  T1. Integracion con opencode: MODO PRIMARIO = `opencode serve` persistente
      (el orquestador habla con el servidor local, sin cold-boot por paso).
      MODO FALLBACK = `opencode run --format json` por turno (simple, util para
      smoke tests y entornos sin servidor persistente). Se selecciona por config
      (opencode.mode: "serve" | "run"). El modo ACP queda como evolucion futura.
  T2. Roles (PO, Dev, QA, SM) definidos como AGENTES DE OPENCODE en
      .opencode/agent/ (visibles y editables), con un ejemplo versionado en
      el repo (opencode.example/ o docs/). El orquestador los invoca por nombre.

1. PRINCIPIOS RECTORES DEL NUEVO DISENO
-------------------------------------------------------------------------------
 P1. OPENCODE ES EL MOTOR. El proyecto NO implementa llamadas LLM, ni RAG
     propio, ni scraping con Playwright: solo ORQUESTA (quien actua, con que
     contexto, en que orden) y VISUALIZA (dashboard en tiempo real).
 P2. Un solo orquestador. Nunca mas dos clases ScrumMasterOrchestrator.
 P3. Cero secretos en el proyecto. Ni credentials.json ni apiKey en config:
     la autenticacion de proveedores vive en opencode (~/.local/share/opencode/
     auth.json o variables de entorno de la maquina del usuario).
 P4. Todo input no confiable (LLM, query params, body, artefactos) se sanea
     antes de tocar FS, DOM o procesos. El spawn a opencode usa SIEMPRE
     argumentos validados (nunca interpolacion en shell).
 P5. Sin I/O sincrona en bucles; escrituras de estado ATOMICAS (tmp + rename);
     sin estado compartido en closures del servidor.
 P6. Todo testeable sin motor real: el adapter de opencode se mockea; el smoke
     con motor real es un script aparte.
 P7. Cero archivos de mapas/temporales commiteados (ver FASE 0).
 P8. Cada fase = commits pequenos reversibles con mensaje "phase-N: ...".
